# Full package-name sweep: every package installed by the live-sdk build
# chain, checked against Devuan's real daedalus package indexes

Triggered by a real CI failure: bootstrap succeeded, base system installed,
then stage3/base_packages install failed with "Package btrfs-tools is not
available, but is referred to by another package." Confirms the exact
category of bug the whole live-sdk rebase was meant to get away from -
just living in a different vendored file than LB_MODE was.

## Method

Every `apt-get install` call site in libdevuansdk's own source that's on
build_iso_dist's call path was enumerated first (grepped directly -
zlibs/bootstrap has 3, zlibs/iso has 1, nothing else touches apt-get
install anywhere in bootstrap/helpers/iso):

    zlibs/bootstrap:103  apt-get install ${core_packages}
    zlibs/bootstrap:104  apt-get install ${base_packages}
    zlibs/bootstrap:148  apt-get install ${extra_packages}
    zlibs/iso:32         apt-get install dialog live-boot live-boot-initramfs-tools

Then every package name feeding those four calls - from libdevuansdk's own
root config (core_packages/base_packages), live-sdk's own root config
(extra_packages baseline), and this blend's own config
(extra_packages additions) - was checked against a real download of
Devuan's daedalus package indexes (main, contrib, and non-free
components, binary-amd64), the same http://deb.devuan.org/merged mirror
already SHA256-verified elsewhere in devuan-build-docs/. Also grepped
overlays/, parental-tools/, launcher/, and iso-builder/live-sdk/ for any
other apt-get/dpkg install call: only familyos.blend's own Plymouth
attempt (already covered below) exists.

## Obsolete/nonexistent package names found (real bugs, all fixed)

Package: btrfs-tools
  Source: libdevuansdk/config, base_packages
  Status: DOES NOT EXIST in daedalus (checked main - confirmed absent)
  Real name: btrfs-progs (confirmed present, version 6.2-1+deb12u2)
  Fix: excluded outright (not renamed) - FamilyOS has no btrfs requirement
  anywhere (squashfs+overlayfs live filesystem, ext4/FAT persistence
  partition), so there's no reason to carry any btrfs tooling at all on
  storage-constrained target hardware.
  This is the package that broke the real CI build.

Package: git-core
  Source: libdevuansdk/config, base_packages
  Status: DOES NOT EXIST in daedalus (checked main - confirmed absent).
  This is the pre-2009 Debian package name for git, merged into a single
  "git" package long before daedalus existed.
  Real name: git (confirmed present in the index alongside the check)
  Fix: swapped for the current name - nothing suggests libdevuansdk meant
  to NOT have git available, so this one is a rename, not an exclusion.

Package: firmware-linux
  Source: live-sdk/config (live-sdk's own root config, sourced
  unconditionally by the `sdk` file for every build - not something a
  blend controls or that libdevuansdk touches)
  Status: DOES NOT EXIST in daedalus - checked all three components that
  could plausibly carry it (main, contrib, non-free); absent from all
  three. Debian 12/bookworm reorganized non-free firmware packaging around
  a new non-free-firmware archive component (which daedalus's mirror
  config here doesn't even enable) - predates daedalus by about two years
  and libdevuansdk hasn't been touched since 2021, well before this
  reorganization. "firmware-linux" as a single umbrella metapackage
  doesn't survive it.
  Fix: excluded outright - libdevuansdk's own base_packages already
  includes firmware-linux-free (DFSG-free, confirmed present in main)
  separately, so removing the broken duplicate is not a net loss of
  firmware coverage.

Package: linux-image-686 (i386 only - does not affect the current
amd64-only CI build, but a real latent bug for a future i386 build)
  Source: live-sdk/config (its own `case "$arch" in i386) ...` block)
  Status: EXISTS (confirmed for i386 in
  devuan-build-docs/confirmed-kernel-packages.txt from earlier work), but
  is the non-PAE kernel flavour - the same wrong-flavour issue already
  documented for the live-build profiles
  (iso-builder/live-build/i386/auto/config's own comment). Installing it
  ALONGSIDE this blend's own correct linux-image-686-pae doesn't fail the
  build, but defeats the entire point of choosing 686-pae for single-core
  Atom netbooks.
  Fix: excluded before this blend's own kernel-package case block adds the
  correct one.

## systemd dependency check (Depends:, not Recommends:)

None of the above packages have a hard `Depends: systemd` or
`Depends: systemd-sysv`. sysvinit-core (Depends: initscripts, sysv-rc |
openrc | file-rc, sysvinit-utils, mount, debconf, libc6, libselinux1)
actively Conflicts: runit-init, systemd-sysv - confirming the fail-safe
non-systemd choice is real, not just a naming convention.

Two categories worth noting but NOT flagged as violations:

- libsystemd0 appears in openssh-server's and elogind's Depends
  (`libsystemd0`, and elogind separately Depends on `dbus`). This is
  systemd's client LIBRARY, not the systemd init daemon/PID 1 - Devuan
  explicitly maintains compatible builds of packages that only need
  libsystemd0's ABI for optional logging/socket-activation integration,
  without requiring systemd actually running. This is standard,
  intentional Devuan practice (the entire reason elogind and Devuan's own
  systemd-shim lineage exist), not a hole in the init-freedom premise.
- init-system-helpers (Pre-Depends of openssh-server, sudo, rsync, screen,
  zsh) is a Debian-maintained abstraction package that supports
  sysvinit/systemd/upstart/openrc alike - not systemd-specific.

No package in this sweep depends on systemd as an init system. The
init-freedom premise this project is built on is intact.
