# Verification: live-sdk / libdevuansdk as Devuan's real build tooling,
# and the mechanism research behind iso-builder/live-sdk/

Confirms the claims behind the rebase from live-build to live-sdk
(iso-builder/live-sdk/) - sourced from reading the real live-sdk and
libdevuansdk source directly (cloned from github.com/devuan/live-sdk and
github.com/devuan/libdevuansdk, which mirror parazyd/live-sdk and
parazyd/libdevuansdk) and from Devuan's own real release archive, not
assumed from the rebase premise.

## 1. Is live-sdk really Devuan's official tool?

CONFIRMED directly. files.devuan.org/devuan_daedalus/desktop-live/README_desktop-live.txt
and .../minimal-live/README_minimal-live.txt (Devuan's own real release
archive, fetched directly) both say the images were "Built with the Devuan
SDK, live-sdk module by jaromil and parazyd." This is not a hearsay claim
from a forum post - it's the README shipped inside the real ISOs.

CAVEAT: the actual daedalus-era blend definitions that produced those real
ISOs are not published anywhere reachable. The GitHub mirrors
(github.com/devuan/{live-sdk,libdevuansdk}) only bundle example blends
current as of beowulf (Devuan 3, ~2019) / chimaera (Devuan 4, Nov 2021) -
neither repo has a single commit or file mentioning daedalus, excalibur, or
bookworm. fsmithred's own public blend tarball drops
(distro.ibiblio.org/refracta/files/blends/) stop at beowulf-blend.tar.gz
(2019) and blends_3.0.0.tar.gz (2020). A dev1galaxy.org forum thread
confirms fsmithred distributed blends this way and separately mentions
live-sdk "getting a complete re-write." The canonical host named in that
same thread, git.devuan.org/devuan-sdk/live-sdk (or sdk/live-sdk), is
behind an Anubis proof-of-work anti-bot challenge (confirmed directly -
curl/WebFetch get served a JS challenge page, HTTP 200, not real content)
that cannot be solved without an actual browser executing JavaScript.
**This is a genuine, unresolved gap** - stated as "not found in any source
checked," not as "does not exist."

Practical consequence: iso-builder/live-sdk/blends/familyos/ is written
from scratch, using the stale beowulf/ascii example blends only as a
structural template (config array syntax, blend_preinst/postinst shape,
chroot-script helper, rootfs/isolinux overlay convention) - not as a
working daedalus base, because no such base is available to us.

## 2. Non-interactive CI operation - CONFIRMED, the one condition that would
have been a hard blocker.

Independently traced (twice - once directly, once by an independent
critique pass) the full build_iso_dist() call graph in
libdevuansdk/zlibs/helpers: bootstrap_complete_base -> blend_preinst ->
iso_prepare_strap -> iso_setup_isolinux -> iso_write_isolinux_cfg ->
blend_postinst -> iso_squash_strap -> iso_xorriso_build. Grepped every
file in that path (zlibs/bootstrap, zlibs/helpers, zlibs/iso, zlibs/imaging,
zlibs/vm, zlibs/sysconf, lib/zuper/zuper) for read/vared/select/TTY
dependencies: zero hits in the actual build path. (zuper's internal
`sysread` builtin is used by unrelated helper subsystems - zkv.save,
rest.put - never called by build_iso_dist.) chroot-script(), the helper
used for everything that runs inside the target chroot, explicitly forces
DEBIAN_FRONTEND=noninteractive, a fixed SOURCE_DATE_EPOCH, LC_ALL=C, LANG=C
on every script it runs.

Confirmed non-interactive operation, but NOT via `load devuan familyos
daedalus` as this section originally stated - see the addendum to finding
#5 below for why that specific invocation doesn't work, and
iso-builder/live-sdk/README.md for the real one.

SUBTLE CORRECTNESS REQUIREMENT (caught by the CI-workflow critique pass,
verified empirically with a reproduction script): `zuper.init`'s variable
tracking (`typeset -h $_v` over the declared vars/arrs/maps) zeroes out
those variables - release, workdir, strapdir, etc. - for the remainder of
the CURRENT FUNCTION's scope if executed from inside a zsh function
(confirmed by reproduction: the value reads back empty inside the
function, and only returns once the function exits). live-sdk's real
`load()` gets away with this because it's a function that returns before
`build_iso_dist` is ever called from the outer interactive session. This
blend's CI invocation (iso-builder/live-sdk/README.md,
.github/workflows/build-iso.yml) replicates load()'s work - including the
final `source "$R/lib/zuper/zuper.init"` and `build_iso_dist` call -
entirely at the TOP LEVEL of `zsh -f -c '...'`, not wrapped in a function,
which is why it works: `typeset -h` never shadows anything at the top
level. Wrapping that invocation in a shell function (e.g. to reuse it for
both amd64 and i386 in one script) would silently reintroduce this bug.

## 3. No LB_MODE-equivalent host-OS auto-detection bug class exists here.

live-build's entire debootstrap/mirror/kernel-package/casper bug chain
traced back to ONE root cause: LB_MODE auto-detected from the build host's
lsb_release. Read every file in libdevuansdk (zlibs/bootstrap, zlibs/
helpers, zlibs/iso, zlibs/imaging, zlibs/vm, zlibs/sysconf, root config)
and live-sdk's own lib/zuper/zuper directly, grepped all for lsb_release/
os-release/uname: the only hit is a `uname -m` in qemu_install_user (an
arm cross-bootstrap host-CPU check, in the build_arm_dist path only -
never called by build_iso_dist). No host-OS auto-detection mechanism
exists anywhere in this codebase. Every package name, mirror URL, and
release string in a blend or config is a literal value the author writes -
there's no switch to accidentally inherit an Ubuntu-flavored default from.

## 4. debootstrap's --foreign mode does NOT avoid the suite-script problem
already fixed for live-build.

libdevuansdk/zlibs/bootstrap's bootstrap_complete_base() calls:

    sudo debootstrap --keyring=... --foreign --arch "$arch" "$release" "$strapdir" "$mirror"

then later `chroot "$strapdir" /debootstrap/debootstrap --second-stage`.
--foreign only defers debootstrap's in-chroot second stage; stage 1
(host-side) still resolves /usr/share/debootstrap/scripts/$release before
it ever touches the chroot - confirmed by reasoning through debootstrap's
own documented --foreign semantics (defers stage 2 execution, not stage 1's
script lookup). This repo's own confirmed-debootstrap-scripts.txt (from the
live-build fix work) already proves Devuan's real debootstrap package has
scripts/daedalus -> scripts/ceres as a symlink that Ubuntu's stock
debootstrap lacks. Same exact CI fix (install Devuan's own debootstrap from
pkgmaster.devuan.org, apt-mark hold) carries over unchanged - this isn't
new work, it's the same fix reused.

One genuine improvement over live-build here: libdevuansdk bundles its own
devuan-keyring via a git submodule (extra/devuan-keyring ->
salsa.debian.org/parazyd/devuan-keyring.git) and passes it explicitly via
--keyring=.../devuan-archive-keyring.gpg, rather than depending on the host
apt having devuan-keyring installed system-wide the way live-build's
--keyring-packages flag required.

## 5. load()'s signature does not match its own README's quickstart example.

sdk (live-sdk's root file): `load() { os="$1"; blend="$2"; [[ $# -gt 2 ]] &&
release="$3"; req=(os arch); ... }` - arch is NOT a positional argument to
load; it must already be set (via the config file) before load runs.
README.md's own quickstart literally shows `load devuan amd64`, which
passes blend="amd64" - not a registered blend_map key (only
devuan-desktop-live, devuan-minimal-live, heads, decode are registered).
This is a soft failure (`act "No blend specified"`, not `die`), so the
documented example actually demonstrates a blend-less bootstrap.

ADDENDUM (caught by an independent critique pass reviewing the actual
blend written from this research, not by this research pass itself): this
section originally concluded the "confirmed correct form" was
`load devuan familyos daedalus`. That is WRONG, for the exact same
reason the README's own example is wrong: `blend_map` is a literal,
hardcoded zsh array assigned INSIDE `load()`'s own function body -

    blend_map=(
        "devuan-desktop-live"  "$R/blends/devuan-desktop-live/devuan-desktop-live.blend"
        "devuan-minimal-live"  "$R/blends/devuan-minimal-live/devuan-minimal-live.blend"
        "heads"        "$R/../heads.blend"
        "decode"       "$R/../decode.blend"
    )

"familyos" is not a key in it and cannot become one without editing
live-sdk's own `sdk` file - there is no external registration mechanism.
`load devuan familyos daedalus` hits the identical silent
"No blend specified" trap as the README's own broken example. Since
patching a vendored third-party file to add a blend_map entry is worse
than not depending on the lookup at all, iso-builder/live-sdk's actual CI
invocation (.github/workflows/build-iso.yml) and README.md bypass
`load()` entirely and replicate its real work directly against this
blend's own known path: source the devuan os-lib, source familyos.blend
directly, set BLEND=1, compute workdir/strapdir - the same steps
`load()` performs internally, minus the hardcoded lookup.

Because blend config files hardcode `arch="amd64"` as a plain assignment
(not `${arch:-amd64}`), building for i386 with the stock convention means
hand-editing the file before each build. iso-builder/live-sdk/blends/
familyos/config instead uses `arch="${ARCH:-amd64}"` so CI can set it per
run without editing the file - a deliberate, documented deviation from the
example blends' own style.

SEPARATE ADDENDUM, same critique pass: libdevuansdk's own root config
computes `image_name`/`vm_name` once, textually, from
`${os}/${release}/${version}/${arch}/${blend_name}` at the point IT is
sourced - which happens BEFORE this blend's own `config` overrides those
same variables (load()'s/the bypass snippet's sourcing order is: os-lib
first, blend second). Plain zsh assignment doesn't re-evaluate on later
variable changes, so without an explicit re-assignment, the built ISO's
filename would silently stay stamped "devuan_chimaera_4.0.0_${arch}"
regardless of this blend's release=daedalus/version=5.0.0 overrides.
iso-builder/live-sdk/blends/familyos/config now recomputes both
`image_name` and `vm_name` itself, after every value they depend on has
its final value.

## 6. iso zlib functions (libdevuansdk/zlibs/iso) - what a blend actually
needs to provide.

- iso_prepare_strap: apt-get installs `dialog live-boot
  live-boot-initramfs-tools` inside the chroot UNCONDITIONALLY, regardless
  of blend package lists. Corrects an earlier open question: our blend does
  NOT need to explicitly list live-boot - it's guaranteed by SDK core, not
  by a Recommends chain that might not hold.
- iso_setup_isolinux: expects $strapdir/boot/vmlinuz*/initrd* to already
  exist (from the kernel package install during bootstrap_stage4) and
  copies live-sdk's own bundled extra/syslinux/{isolinux.bin,*.c32} into
  $workdir/binary/isolinux/ - confirmed present on disk in the cloned repo,
  reusable as-is, no vendoring needed in this repo.
- iso_write_isolinux_cfg (core default): hardcodes a single boot label with
  no blend-exposed kernel-append hook - this is why familyos.blend defines
  its own override (same pattern devuan-minimal-live.blend uses) rather
  than relying on any core-provided customization point.
- iso_squash_strap: hardcodes `mksquashfs -comp xz` (arch-conditional
  -Xbcj), not blend-configurable - accepted as-is, no FamilyOS requirement
  conflicts with it.
- iso_xorriso_build: BIOS-only unless $MKEFI is set. If set, it expects
  binary/boot/grub/efiboot.img to already exist, which nothing in the
  default call chain creates - a real landmine for any blend that sets
  $MKEFI without separately populating that file first.
  iso-builder/live-sdk/blends/familyos does NOT set MKEFI, which both
  avoids this landmine and matches the target hardware (old BIOS-era
  machines and netbooks per Project_Vault/_Base Architecture Overview.md -
  no UEFI requirement exists for this project).

## 6b. Commit pinning: live-sdk @ 4f4b7c25a9ef4fc2fa7378fc338ba7cf0722662d,
libdevuansdk @ 7eb4f578833f4b093e224633176a12a214dec300

CI pins live-sdk to its own current HEAD, then runs `git submodule update
--init --recursive --checkout` to pull lib/libdevuansdk - which resolves
to 7eb4f578..., an OLDER commit than the standalone libdevuansdk repo's own
HEAD (da21506..., "update to build chimaera") that section 1's research
was originally read against. Confirmed 7eb4f578... is a direct ancestor of
da21506... (`git merge-base --is-ancestor` exit 0). Not re-pinned to the
newer standalone HEAD - live-sdk's own designated submodule commit is the
pairing actually exercised together, and is what CI's `git submodule
update` naturally produces.

CORRECTION (caught by the CI-workflow critique pass, not claimed
accurately anywhere before this): the commits between 7eb4f578... and
da21506... are NOT all irrelevant to build_iso_dist's call path. Commit
5603716 ("Mount the host sys,dev,dev/pts as read-only for bootstrap")
modifies devprocsys() in zlibs/helpers, which chroot-script() uses - and
chroot-script is squarely on build_iso_dist's path (every blend_preinst/
blend_postinst chroot-script call in familyos.blend depends on it). This
does not change the pinning decision (live-sdk's own submodule reference
is still the correct pairing to use, regardless of what's newer upstream),
but the original claim that the intervening commits were all irrelevant
was wrong and is corrected here rather than left standing. The rest of the
range (3013804, e3bf866, 833fb2b, 3e8d9f6, 3e68795, 27175c1, 1952888,
424a396, 25a86b7, 3cffb94, 7b9e097, 647e0f6, and the arm/vm-imaging-only
commits before them) are genuinely out of build_iso_dist's ISO path -
license headers, docs, F2FS/arm/vm-image support, purge-list and
version-string tweaks, console-output quieting, and defensive checks in
zlibs/imaging - just not devprocsys/chroot-script's read-only-mount change.

## 7. Phase 2/3 blend-content findings from the critique passes

- `libdevuansdk`'s own `core_packages` (its root config) lists plain
  `sysvinit`, not `sysvinit-core` - the package that actually installs as
  PID 1 on a modern Devuan release. `iso-builder/live-sdk/blends/familyos/config`
  now lists `sysvinit-core` explicitly in `extra_packages`
  (redundant-but-safe if libdevuansdk's own default turns out fine, not
  redundant if it doesn't) - matching this repo's old
  `familyos.list.chroot`, which always listed it explicitly for the same
  reason.
- The old `familyos.list.chroot`'s `live-config-systemd-` de-select guard
  (Debian bug #772651: live-config resolving to live-config-systemd
  instead of live-config-sysvinit) does NOT carry over as an
  `extra_packages` entry the way it looks like it should: `bootstrap_stage4`
  (`libdevuansdk/zlibs/bootstrap`) pre-flights every `extra_packages` entry
  with an exact-match `apt-cache search` existence check before installing
  anything, with no special-casing for apt's own trailing "-" removal
  syntax - `live-config-systemd-` would be reported as a nonexistent
  package and hard-fail the entire build (confirmed by reading the
  preflight loop directly - this was caught before being committed, not
  by a critique pass). The same protective intent is applied instead as an
  explicit `apt-get purge -y live-config-systemd` in familyos.blend's
  finalize script, which runs after stage4 and isn't subject to that
  preflight check.
- `iso_setup_isolinux` copies `$strapdir/boot/initrd*` to
  `$workdir/binary/live/initrd.img` BEFORE `blend_postinst` runs (per
  `build_iso_dist`'s fixed call order) - if `blend_postinst`'s
  `update-initramfs -u` (run for the optional Plymouth theme) actually
  regenerates the initrd, that copy is stale and the ISO would boot with
  an initrd that has no Plymouth theme in it. `familyos.blend` now
  re-copies `$strapdir/boot/initrd.img` to
  `$workdir/binary/live/initrd.img` again at the end of `blend_postinst`,
  after the finalize script (and its conditional `update-initramfs`) has
  run. Cosmetic (Phase 4 concern, not a security/fail-safe regression) -
  found by an independent critique pass.

## 8. Confidence caveat

Nothing here has been build-tested. Same sandboxing limitation already
documented for live-build (this authoring environment's proot-based
Android/Termux backend can't run debootstrap/mksquashfs/loopback-mount
pipelines at all) applies equally here, compounded by the lack of any
working daedalus-era reference blend to check the result against (unlike
live-build's daedalus/ceres symlink, which could be proven against a real
shipped .deb). Everything above is verified by reading source and by an
independent critique pass re-deriving each claim from the same source - not
by a real build. Treat the first real CI run as the actual test of this
work, the same way it was for the live-build fixes.
