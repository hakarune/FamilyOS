# Browser base, curated-homepage architecture, and the BRAVE+/KidzTube/
# Starfall/Ducksters domain questions - what was confirmed, what
# wasn't, and why.

## Confirmed browser base

launcher/browser_kiosk.py is NOT a standalone browser application
(Firefox, Epiphany, Chromium-the-app, Min, Falkon, or otherwise) -
confirmed by reading iso-builder/live-sdk/blends/familyos/config's
extra_packages (no browser package listed there) and build.log (no
Firefox/Chromium/epiphany/min/falkon package ever installed). The only
thing installed is python3-pyqt5.qtwebengine
(devuan-build-docs/confirmed-package-sweep.txt), which bundles Qt5
WebEngine's own Chromium build (~87, unbranded - see browser_kiosk.py's
own header comment). The "browser" is 100% custom FamilyOS code (a bare
QWebEngineView with no browser-chrome layer at all) embedding that
Chromium engine - not a configuration of an existing browser app. See
launcher/README.md's "Tech decisions" for why Min/Falkon were rejected.

## Curated-homepage architecture (this round's build)

Previously: a single hardcoded ALLOWED_HOSTS set (kidzsearch.com only)
and a fixed HOME_URL. Now: a parent-editable list at
/var/lib/familyos/allowed-sites.json (managed via the Parent Panel's
"Allowed Websites" section -> parental-tools/familyos-sites, which
shells out to lib/sites-edit.py for the actual JSON add/remove and
lib/render-homepage.py to regenerate the local tile page after every
change), seeded at build time from overlays/etc/familyos/default-websites.json
(KidzSearch, BRAVE+, Starfall, Ducksters - see docs/default-websites.md
for the selection criteria) so the Toddler flavor works before any
customization. browser_kiosk.py loads
ALLOWED_HOSTS from this file at process start (not live-reloaded mid-
session) and its HOME_URL is now the local generated
file:///var/lib/familyos/homepage.html, not a hardcoded remote URL.
Persisted the same way /home/toddler/media already is - see
iso-builder/live-build/persistence-media/persistence.conf.

## Homepage/allowlist linkage - edge cases found by independent review

Traced the full add/remove -> allowlist path (sites-edit.py's URL
validation and lowercasing, render-homepage.py, browser_kiosk.py's
_load_allowed_hosts()) and confirmed it's correct for the normal case
(host derived once at add time via urlparse().hostname, lowercased
consistently on both write and read, no case-sensitivity mismatch;
port numbers correctly stripped and consistent with QUrl.host()'s own
port-free behavior; a malformed/missing "host" key on one entry is
skipped rather than treated as a wildcard - fails closed, not open).

Two edge cases were found and addressed:

- **Fixed**: _load_allowed_hosts() previously couldn't distinguish "the
  sites file is missing/malformed" from "the file parsed fine but a
  parent genuinely removed every site" - both fell back to the
  hardcoded _FALLBACK_HOSTS (kidzsearch.com), silently overriding an
  intentional "remove everything" action. Fixed to only fall back on
  an actual read/parse failure or a structurally wrong file (missing
  or non-list "sites" key), not on a legitimately empty list.
- **Not fully resolved, low severity**: whether a Unicode
  (non-ASCII/IDN) hostname a parent might type gets compared
  consistently between how Python's urlparse().hostname stores it
  (literal Unicode, not auto-converted to punycode/ACE form) and how
  Qt's QUrl.host() returns it at navigation-check time is a
  Qt-version-dependent detail that could not be confirmed without a
  real Qt runtime. If there's a mismatch, the practical effect is
  fail-closed (that specific site just wouldn't work, prompting the
  parent to notice and try again), not fail-open - low severity, but
  worth a real test if a non-English-alphabet domain is ever added.

## IMPORTANT: what the host-allowlist actually governs

acceptNavigationRequest (QWebEnginePage's navigation hook) fires for
NAVIGATION events - top-level page loads, link clicks, JS-driven
redirects, and (since this code deliberately does NOT special-case
is_main_frame) iframe loads too. It does NOT fire for sub-resource
fetches an already-loaded, already-allowed page's own scripts make:
video segment requests, XHR/fetch API calls, images, analytics/tracker
beacons. Those go through regardless of ALLOWED_HOSTS, exactly as they
would in any other browser - QtWebEngine simply has no
navigation-request hook for that traffic class.

This matters directly for the "does adding a homepage tile without
adding its CDN to the allowlist create a hole" question: it does NOT,
in the direction of blocking legitimate playback - a video player's own
`<video src="https://cdn.example.com/segment.ts">` or JS-driven
fetch() call to a CDN is a sub-resource load, not a navigation, so it
was never going to be blocked by ALLOWED_HOSTS regardless of whether
that CDN's hostname is listed. The real risk this project's allowlist
protects against is a full-page/iframe navigation to a NON-approved
site or page - which IS still fully covered by extending ALLOWED_HOSTS
to include every host a parent adds via familyos-sites (confirmed:
browser_kiosk.py's _load_allowed_hosts() reads every "host" field from
the JSON file with no filtering/omission).

The system-level DNS lockdown (overlays/etc/init.d/familyos-dns-lock)
and DoH-resolver IP blocklist (parental-tools/lib/net-rules.sh) remain
the actual defense against an allowed page's own background network
calls to disallowed third parties (ads, trackers, unexpected CDNs) -
not this browser-level allowlist, which was never designed to cover
that traffic class. This isn't a regression introduced this round -
it's how acceptNavigationRequest always worked, just not previously
written down explicitly.

## Login form submission (BRAVE+ requires an account)

Confirmed this already works with no code change needed: nothing in
browser_kiosk.py disables JavaScript, cookies, or local storage
(QWebEngineSettings defaults for all three are left untouched - only
PdfViewerEnabled is explicitly turned off), and QWebEngineView's
default profile persists cookies normally. A same-origin login form
POST (the common case) is either (a) a same-host navigation, already
covered by ALLOWED_HOSTS once that host is added, or (b) an AJAX/fetch-
based JS login (common in modern single-page apps), which isn't gated
by acceptNavigationRequest at all, per the finding above - it just
works. Confirmed watch.braveplus.com's own /sign_in page is served from
the same origin (watch.braveplus.com), not an external OAuth redirect
domain, via a direct fetch of that page - though this can't fully rule
out a JS-driven cross-origin redirect the fetch tool used here can't
render/execute (it converts HTML to markdown, stripping <script> tags
and form action attributes - a real limitation of the research method,
not a claim of certainty). If BRAVE+'s actual login flow does redirect
the top-level frame to a different domain (not confirmed one way or
the other), that domain would need adding to the allowlist too - watch
for this on first real login attempt.

## BRAVE+ (watch.braveplus.com) CDN findings

BRAVE+ runs on the Uscreen white-label OTT platform - confirmed via its
Android app's package ID, tv.uscreen.braveplus (Google Play listing).
Confirmed one real CDN domain directly from watch.braveplus.com's own
page source: alpha.uscreencdn.com (serving at least the site's logo
image, likely the same domain family used for video assets, following
Uscreen's own *.uscreencdn.com convention). Uscreen's own help docs
state they use "a global blend of CDNs" (multiple regional providers/
endpoints), meaning there may be additional CDN hostnames beyond
alpha.uscreencdn.com that only a live, authenticated playback session
would reveal - NOT fully enumerable from published documentation or an
unauthenticated page fetch.

Per the acceptNavigationRequest finding above, this is very likely a
non-issue for actual video playback in the first place: if BRAVE+'s
player streams video via a `<video>` element or JS fetch() calls to its
CDN (the standard modern-web pattern, not an iframe-based embed), those
are sub-resource loads that were never going to be blocked by
ALLOWED_HOSTS regardless. **Open item for real testing**: log into
BRAVE+ in the actual FamilyOS kiosk browser and confirm video actually
plays. If it doesn't, the failure is more likely to be an iframe-based
embed (which WOULD be blocked, per the navigation-vs-subresource
finding) than a missing CDN entry in ALLOWED_HOSTS - check for that
specifically before assuming more allowlist entries are the fix.

## KidzTube domain findings

Confirmed KidzTube is a section of kidzsearch.com itself
(kidzsearch.com/kidztube/...), not a separate domain - already fully
covered by the existing kidzsearch.com/www.kidzsearch.com allowlist
entries, no additional host needed for KidzTube's own pages.

Confirmed (via web search, kidzsearch.com itself blocks automated page
fetches so this could not be verified by directly reading its source)
that KidzTube curates and filters YouTube content rather than hosting
video files itself - i.e. video playback happens through YouTube's own
embed player. Standard YouTube embeds are `<iframe>`-based, and since
this code's acceptNavigationRequest deliberately does not special-case
is_main_frame, an iframe's own navigation to youtube.com is checked by
the exact same mechanism as top-level navigation - meaning without an
explicit allowance, KidzTube videos would likely fail to play entirely
(blocked iframe), unlike BRAVE+'s likely sub-resource-based playback.

Fixed: added a separate, non-parent-editable TRUSTED_EMBED_HOSTS set in
browser_kiosk.py (www.youtube.com, www.youtube-nocookie.com - both
included since the exact domain KidzSearch's embed code uses wasn't
confirmable) alongside the parent-curated ALLOWED_HOSTS, so an embedded
player's iframe navigation succeeds. Deliberately kept separate from
the Parent Panel's site list so a parent doesn't see "youtube.com"
listed as if it were a site they approved as a destination - it's
approved only as embed-rendering infrastructure for KidzTube.

**Fixed (was a real gap, caught by independent review): TRUSTED_EMBED_HOSTS
no longer allows youtube.com/youtube-nocookie.com as a full top-level
destination.** The first version of this allowed those two hosts for
ANY navigation, main-frame or not - since acceptNavigationRequest can't
tell "this is a KidzTube video's own iframe" from "this is a link
pointing straight at youtube.com," that meant a child could reach the
full, unrestricted YouTube site (not just have an embedded video
render) via any link on an allowed page or an embedded player's own
"Watch on YouTube" branding, and once there, browse all of YouTube
freely for the rest of that browser session - a materially broader hole
than "a residual embed-branding risk." Fixed by actually using
acceptNavigationRequest's is_main_frame parameter (previously ignored):
TRUSTED_EMBED_HOSTS is now only honored when `is_main_frame` is False -
i.e. only as an iframe embed, never as the addressable top-level page.
A top-level navigation to youtube.com is now rejected exactly like any
other non-allowlisted host, same as before TRUSTED_EMBED_HOSTS existed.

**Still NOT fully resolved**: an embedded player could still expose a
button/control that opens a NEW top-level navigation via JavaScript
(`window.location`, not an iframe load) rather than a plain anchor
link - that would correctly be rejected by the same is_main_frame check
now in place, so this doesn't reopen the fixed hole, but it hasn't been
confirmed one way or the other whether KidzTube's actual embed does
this. Live-test by playing an actual KidzTube video in the built
browser and checking whether any YouTube branding element is clickable
at all, and if so, what happens when clicked (it should simply fail to
navigate, per the fix above - confirm that's what's actually observed).

## Starfall (starfall.com) findings

No login required for core content: confirmed via web search ("all of
the basics for learning how to read are available to everyone for
free") and independently via a direct fetch of starfall.com/h/ itself.
A paid membership exists for additional content, gated behind
secure.starfall.com, but isn't required for the core free activities
this project defaults to.

Genuinely ad-free: confirmed directly from the site's own text ("Starfall
has no advertising, does not collect personal information from
children, does not sell any information, and uses cookies only for
internal website management") - not just a search-result summary, the
page's own self-description.

CDN/asset domains: a direct fetch of an actual interactive activity
page (starfall.com/h/ltr-a/a-song/) found all assets self-hosted under
starfall.com's own subdomains (www.starfall.com,
_images/ paths) - no third-party CDN or game-hosting platform
referenced. Other starfall.com subdomains exist (secure.starfall.com -
paid membership/login; teach.starfall.com - educator resources;
store.starfall.com - merchandise; help.starfall.com - support docs) but
aren't needed for the free core content this project defaults to, so
only www.starfall.com is in the default allowlist entry - a parent
could add the others manually if they want the paid/teacher features.

Not confirmed without live testing: whether every free interactive
activity stays entirely on www.starfall.com or whether some specific
activity redirects through secure.starfall.com even for free content
(the research method here - WebFetch converts HTML to markdown/text,
stripping script tags - can't fully rule this out, same disclosed
limitation as the BRAVE+/KidzTube research below).

## Ducksters (ducksters.com) findings

No login required for core content: confirmed via web search and a
direct fetch of ducksters.com's games listing page - all games are
plain internal links (e.g. /games/math_games.php), not gated behind a
login redirect.

NOT ad-free - a confirmed, disclosed exception to this list's own
selection criteria (see docs/default-websites.md): Ducksters' free
tier explicitly discloses, in its own footer text (confirmed via a
direct page fetch, not just a search summary), "ads powered by ...
COPPA compliant Playwire Kid's Club." An ad-free tier ("Ducksters
Premium") exists but requires a paid account created by an adult 18+,
which doesn't fit a no-signup default. This was surfaced to and
confirmed with the project owner before deciding to include Ducksters
as a default anyway, with this exception documented rather than
silently shipped or silently dropped.

CDN/asset domains: a direct fetch of the games listing page found no
external game-hosting platform or CDN domain referenced - games appear
self-hosted directly under ducksters.com. The one external domain found
at all is playwire.com (the ad network above, referenced only in
footer text, not as a script/iframe source visible to this fetch
method). Not confirmed without live testing whether the ad network
itself loads via an iframe from a specific playwire.com/googlesyndication-
style subdomain that would need explicit handling if this project ever
wanted to actually suppress the ad content itself (out of scope for
this round - the allowlist governs navigation, not ad-iframe
sub-resource loads, per the finding above; blocking specific ad-network
resource loads would need a different mechanism entirely, e.g. a
QWebEngineUrlRequestInterceptor, not attempted here).
