## The actual root cause: LB_MODE auto-detection

usr/share/live/build/functions/defaults.sh, lines 99-126: when `--mode`
isn't passed, LB_MODE is auto-detected from the *build host*, not the
target distribution:

    if [ -x /usr/bin/lsb_release ]
    then
        _DISTRIBUTOR="$(lsb_release -is | tr "[A-Z]" "[a-z]")"
        case "${_DISTRIBUTOR}" in
            debian|progress-linux|ubuntu|devuan)
                LB_MODE="${LB_MODE:-${_DISTRIBUTOR}}"
                ;;
            ...

On GitHub Actions' `ubuntu-latest` runner, `lsb_release -is` prints "Ubuntu",
so LB_MODE silently resolves to "ubuntu" - regardless of --distribution
daedalus. This one variable then drives roughly 20 separate `case
"${LB_MODE}"` branches throughout defaults.sh, including every default this
project has had to individually patch around so far:

    LB_INITRAMFS       (line ~255-266): ubuntu -> casper,       * -> live-boot
    LB_LINUX_PACKAGES  (line ~686-694): ubuntu -> "linux",      * -> "linux-image"
    LB_MIRROR_BOOTSTRAP (line ~405-417): ubuntu -> archive.ubuntu.com, devuan -> packages.devuan.org
    LB_MIRROR_*_SECURITY (line ~441-510): ubuntu -> security.ubuntu.com, debian -> security.debian.org
    LB_KEYRING_PACKAGES (line ~552-566): ubuntu -> ubuntu-keyring, devuan -> devuan-keyring
    LB_ISO_VOLUME, LB_APT_RECOMMENDS, LB_DEBIAN_INSTALLER_GUI, etc.

Grepped `ubuntu)` case branches in defaults.sh: 22 distinct locations.
`--mode devuan` is a value this Devuan-patched package explicitly recognizes
(the same switch above lists debian/progress-linux/ubuntu/devuan) - passing
it pins the whole family of defaults to Devuan's branch in one flag, instead
of overriding each wrong default individually as it's discovered (which is
the pattern the last three fix commits followed). No hardcoded suite
whitelist rejects "daedalus" as a distribution string (only
LB_PARENT_DISTRIBUTION jessie|sid gets special-cased, for
disabling security/updates - daedalus correctly falls into the enabled `*`
case, consistent with the mirror-security fix already in auto/config).

With --mode devuan explicit, LB_LINUX_PACKAGES's own default already
resolves to "linux-image" (same value the explicit --linux-packages
linux-image flag forces) - that flag is very likely now redundant, but is
left in place rather than removed without a real `lb build` run to confirm.

## --mode devuan is not purely additive: two side-effects pinned back

Full enumeration of all ~20 `case "${LB_MODE}"` blocks in defaults.sh (not
just the LB_INITRAMFS one) found two more defaults that flip between the
previous implicit "ubuntu" mode and explicit "devuan" mode, neither already
covered by an existing auto/config flag:

    LB_APT_RECOMMENDS:            true (implicit ubuntu, `*` case) -> false (devuan's own case)
    LB_FIRMWARE_CHROOT/BINARY:    false (implicit ubuntu, own case) -> true (devuan, `*` case)

Both land in the chroot package-install stage that CI has already gotten
through successfully under the old implicit mode. LB_APT_RECOMMENDS=false
could silently drop packages previously pulled in only via Recommends;
LB_FIRMWARE_CHROOT/BINARY=true is a previously-unexercised code path that
would attempt to pull firmware packages into a build whose --archive-areas
is pinned to "main" only (non-free firmware isn't in main). Both
auto/config scripts now pin --apt-recommends true --firmware-chroot false
--firmware-binary false explicitly, alongside --mode devuan, so this
change stays scoped to the one default it's meant to fix.

Every other LB_MODE-driven default in the file was checked and is either
already pinned by an explicit auto/config flag (mirrors, keyring,
initsystem, linux-packages, archive-areas, distribution - so mode never
reaches the fallback default) or cosmetic-only with no build-success impact
(LB_ISO_APPLICATION/PUBLISHER/HDD_LABEL/VOLUME label strings, LB_ROOT/
LB_NET_ROOT_PATH netboot paths - unused, bootappend-live uses persistence
not netboot). LB_DEBIAN_INSTALLER defaults to false unconditionally
(not mode-dependent) and is never passed, so its GUI/loadlin/win32-loader
mode-driven sub-defaults are moot either way.

## Known caveat: live-build is not Devuan's official ISO build tool

Devuan's own GitLab tracker documents this exact package's rough edges -
devuan-packages/live-build#13 ("live-build uses debian repos"): out of the
box it defaults to debian-archive-keyring and Debian mirrors, and pulls in
live-config-systemd (unmet dependency on a sysvinit system) unless overridden.
This project's auto/config already independently avoids all three symptoms
via its existing explicit --keyring-packages devuan-keyring,
--mirror-bootstrap/--mirror-binary/--mirror-*-security, and --initsystem
sysvinit flags - so --mode devuan doesn't newly introduce reliance on a
broken default here, it closes the specific LB_INITRAMFS/LB_LINUX_PACKAGES
gap that wasn't yet covered.

Separately, per Devuan's own community documentation (dev1galaxy.org),
Devuan's actually-official live-ISO tooling is `live-sdk`/`mklive`, not this
live-build package at all - live-build is usable on Devuan but was never the
project's primary path, which is consistent with this package's version
being frozen at the initial devuan2 patch level (Feb 2016, "devuan/jessie"
branch) with no later revision for ascii/beowulf/chimaera/daedalus. This
doesn't invalidate the --mode devuan fix (the CLI options and LB_MODE
behavior above are directly verified against the real package this CI job
would install), but a full switch to live-sdk would be a materially larger
change than this fix and is out of scope here - flagged for awareness, not
acted on.
