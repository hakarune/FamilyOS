# Parent account password: build-time preseed mechanism, why it's
# safe, and the in-app change-password flow that makes it a permanent-
# enough solution rather than just a testing stopgap.

## Background

The `parent` account was always created locked (`passwd -l parent`,
no valid password hash at all) - deliberately, so nothing ever
silently baked in a default credential. This meant the entire
Parent Panel auth flow (require_parent_auth -> pamtester ->
pam_unix.so) had nothing to actually authenticate against on a real
built image: no password typed into the GUI's "Enter parent password"
field could ever succeed. This was a known, intentionally-deferred gap
(see the old comment in
iso-builder/live-build/common/hooks/live/0010-create-accounts.hook.chroot:
"setting a real parent password is a Phase 3/4 first-boot-wizard or
build-time preseed responsibility") - this round implements the
build-time-preseed half of that, plus a real in-app way to change it
afterward (the first-boot-wizard idea is still logged separately in
docs/future-ideas.md).

## The mechanism

`iso-builder/live-sdk/blends/familyos/familyos.blend`'s `blend_preinst`
checks for a `FAMILYOS_PARENT_PASSWORD` environment variable when
creating the `parent` account:

- **Not set** (the default): `parent` is created locked, exactly as
  before. Nothing changes for a build that doesn't opt in.
- **Set**: `parent` is created and then given that password via
  `chpasswd`, instead of being locked.

`toddler` is unaffected either way - always locked, autologin-only, no
password preseed mechanism exists or should exist for it.

## Why this is safe: the value never gets traced or logged

This took real care to get right, not just "pipe the env var into a
shell command":

1. **Injection safety**: the env var crosses from a host-side zsh
   variable into the literal text of a generated `/bin/sh` script that
   runs later, inside the chroot (via libdevuansdk's `chroot-script`
   helper - see zlibs/helpers). A password containing shell
   metacharacters (`$(...)`, `"`, `'`, etc.) must not be interpreted as
   shell syntax when that generated script executes. Verified directly
   (not just reasoned about) by testing zsh's `${(qq)}` quoting flag
   against a deliberately hostile test value containing a command-
   substitution attempt and an embedded quote/apostrophe: the exact
   original string round-tripped through the generated script byte-for-
   byte, with the `$(...)` never executing. `${(qq)}` produces a
   POSIX-sh-safe single-quoted literal (embedded single quotes escaped
   via the standard `'\''` trick) - this is what's actually used in
   familyos.blend, not a plain unquoted substitution.

2. **Trace safety**: libdevuansdk's `chroot-script` helper forcibly
   injects `set -x` into every script it runs (via a `sed` edit right
   after the shebang line), tracing each command to a `<script>.log`
   file that then gets moved to `$R/log/` on the host after the script
   runs. Without a guard, the traced `chpasswd` invocation would write
   the plaintext password into that file. Fixed by wrapping just the
   sensitive line in `set +x` / `set -x` inside the generated script,
   so it's never traced regardless of where the trace log ends up or
   whether a future change to the CI workflow ever uploads
   `live-sdk-src/log/` as an artifact.

3. **Not relying on GitHub's own secret masking as the safety net**:
   confirmed via GitHub's own documentation that automatic secret
   redaction "is not guaranteed" and can fail against transformed/
   structured data - and masking is applied to the live log viewer, not
   guaranteed to scrub an already-written, uploaded artifact file's raw
   bytes. The mitigations above (injection-safe quoting, trace
   suppression) mean the password is never written to any stream or
   file that could end up in `build.log` or an uploaded artifact in the
   first place - not relying on redaction to catch it after the fact.

4. **What DOES still exist after a build, and why that's fine**: with
   `DEBUG=1` set (required for the verify step - see
   confirmed-live-sdk.txt), the bootstrap tree (`strapdir`, including
   its `/etc/shadow`) survives on the runner's disk until the job ends.
   `/etc/shadow` only ever contains a *hash* of the password (computed
   by `chpasswd` itself), never the plaintext - this is the same
   exposure any real system's `/etc/shadow` has, and the GitHub-hosted
   runner is an ephemeral VM destroyed after the job completes. Nothing
   in the CI workflow uploads `live-sdk-src/` itself as an artifact
   (only `build.log` and `live-sdk-src/dist/*.iso`), so this hash never
   leaves the runner at all.

## How to set this for a local build

Export the variable before running the same `zsh -f -c '...'`
invocation `.github/workflows/build-iso.yml` uses (see
`iso-builder/live-sdk/README.md`'s "Invoking a build" section for the
full command):

    export FAMILYOS_PARENT_PASSWORD='your-test-password-here'
    # ... then the normal zsh -f -c '...' build invocation

Unset it (or just don't export it) to get the original locked-account
behavior back.

## How to set this for CI (GitHub Actions)

Add a repository secret, NOT a literal value in the workflow file:

1. Repo Settings -> Secrets and variables -> Actions -> "New repository
   secret".
2. Name: `FAMILYOS_PARENT_PASSWORD`. Value: whatever starting password
   you want the built image to ship with.
3. `.github/workflows/build-iso.yml`'s "Build the FamilyOS ISO with
   live-sdk" step already references
   `${{ secrets.FAMILYOS_PARENT_PASSWORD }}` in its `env:` block - no
   further workflow changes needed. If the secret is never created,
   this evaluates to an empty string and the build falls back to the
   locked-account default automatically.

## The real, permanent mechanism: changing the password in-app

The preseed above is a STARTING password only, not something a parent
is expected to keep relying on indefinitely. `launcher/ui/parent_panel.py`
now has a "Change Parent Password" section:

- Requires the CURRENT password, typed into its own field (never the
  cached password from the panel's initial "Unlock" step) - changing
  the password re-requires proving you know the current one, even from
  inside an already-unlocked panel. This is enforced twice: once
  client-side (the field must be filled in) and for real, server-side,
  by `parental-tools/familyos-set-password`'s own `require_parent_auth`
  call - the actual security gate, not the UI check.
- Requires the new password twice (a plain confirmation-match check,
  to avoid a typo silently locking a parent out) and a minimum length
  (8 characters, checked both client-side for immediate feedback and
  server-side in `familyos-set-password` as the real enforced floor).
- Goes through the same sudo/privileged-script pattern every other
  parent-panel action uses:
  `sudo /usr/local/bin/familyos-set-password`, piping BOTH the current
  and new password via stdin (two lines - current password first,
  consumed by `require_parent_auth`, then the new password) - never via
  argv or an environment variable, same reason as every script in
  `parental-tools/` already documents (`ps` visibility).
- Routes the actual `chpasswd` call through `env-guard.sh`'s
  `run_or_dry_run`, same as every other system-changing action here -
  safe to test on a developer's own machine (prints
  `[DRY RUN] would execute: chpasswd` instead of actually changing
  anything, and the piped password is never included in that message
  since `chpasswd` takes no arguments).

Net effect: a preseeded test password gets a family through first boot,
and the Parent Panel is where they'd actually set the password they
intend to keep using - no rebuild required.
